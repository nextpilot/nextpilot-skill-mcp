## 日志入库方案定稿（09:3x）—— 第 9 节已写入文档

用户最新两条要求：①测试日志放 `tools/` 一起上传仓库用于日志测试；
②CI 增加一条从 `logs.px4.io` 下载多机型多版本 10+ 条日志跑回归。
上一轮的 AskUserQuestion 回答是"用 Git LFS 存大文件"+"CI 不下载，只用手动脚本"。

**Git LFS 被实测否决（关键结论，别再走这条路）**：直接打 gitee 的 LFS batch 端点：

```bash
curl -s -X POST -H "Accept: application/vnd.git-lfs+json" \
  -H "Content-Type: application/vnd.git-lfs+json" \
  -d '{"operation":"download","transfers":["basic"],"objects":[]}' \
  https://gitee.com/nextpilot/nextpilot-skill-mcp.git/info/lfs/objects/batch
```

→ **403** `lfs batch error: lfa auth batch error: LFS only supported repository in paid or trial enterprise.`
对照 `gitee.com/oschina/git-osc.git` 同请求 → **200 `{"objects":[]}`**。
即**端点、请求都对，是服务端按仓库拒绝**（免费/个人仓库不给 LFS）。官方帮助中心那句是对的，

## hook 语言统一方案（10:0x，用户确认）—— 第 12 节已写入文档

用户要求：`pre-commit` 与 `pre-push` 各只留一个 Python 版，**其他全删**。

**关键实测（决定了整个设计，不是推断）**：本机 `python` 解析到**托管 Python 3.13.12**，
它**没有 ruff**（`No module named ruff`）；项目要的是 `C:/Users/zhanfuyu/anaconda3/python.exe`
（ruff 0.16.7）。**这就是 `pre-commit` 在本机曾经坏掉的根因。**

**为什么不能只改 shebang**：`pre-push` 里跑 `python tools/ci/check_all.py`，
而 `check_all.py` 内部用 `sys.executable -m ruff` 跑格式化检查——
若 hook 自己由托管 Python 启动，`sys.executable` 就是托管 Python → **每次 push 都红**。
**结论：hook 必须自己探测解释器。**

**`.ps1` 本来就不会被 Git 调用**：Git 在 Windows 上只认无扩展名 hook 或 `.exe`/`.bat`/`.cmd`。
它的能力已被 `FULL_PUSH=1` / `WITH_E2E=1` 完整覆盖 → **删它零行为损失**（全仓扫过，无调用点）。

**探测口径（写死，不读配置）**：① anaconda python 存在且能 `import ruff` → 用它；
② 回退 `shutil.which("python")`；③ 都不行 → 打印"缺什么" + `exit 127`，**由 Git 放行**。
第 ③ 条是纪律：hook 是提醒，不是把人锁在门外。

**调用口径**：`pre-push` 用裸命令 `"python"`（让子进程继承 PATH）；
`pre-commit` 保留现成的 `sys.executable -m ruff` 写法，只在前置探测里把对的解释器落实成 `sys.executable`。

**Windows 坑**：Git 用 `/bin/sh` 启动 hook，脚本里一律用 `/` 分隔符，
连 `python.exe` 前那节也写 `C:/Users/.../python.exe`（反斜杠会被 sh 吃掉）。

**顺手修正第 11.4 节**：commit-msg 的格式正则**只用圆括号** `(...)`，去掉方括号版本
——方括号在 `sh` 与 Git 配置里是转义地雷，且项目 15 条真实提交只用了圆括号。

## ⚠ 发现并修掉一个真 bug：`--with-e2e` 从来没传出去

**症状**：`WITH_E2E=1 git push` 打印 `--stage push,ci`（看着像要跑 E2E），
**实际两步都静默跳过**；`FULL_PUSH=1` 同理。

**根因**（我今天早些时候改 Python 版 hook 时引入的）：

```python
if os.environ.get("WITH_E2E") == "1" and "ci" not in stages:
    cmd.append("--with-e2e")
```

E2E 两步**住在 ci 阶段里** → 想要 E2E 的每条路径都满足 `"ci" in stages` →
`"ci" not in stages` **恒假** → `append` 一次都不执行。

**修法**：两个维度独立传（`--stage` 管阶段，`--with-e2e` 管步骤）。

**已配守卫 + 自证**：
- `check_hygiene.py` 新增第 6 项「hook 不从阶段列表反推开关」；
- `mutate_guards.py` 新增变异「pre-push 从阶段列表反推 --with-e2e」（42 → 43 条）。

**自证过程本身暴露了两个坑（都值得记）**：

1. **守卫第一版是恒绿的**：正则写成 `with_[a-z_]+`，而开关名是 `with_e2e` ——
   `[a-z_]+` 匹配不到 `2`。在真实 bug 上它报 `OK`。
   **一条永远不红的守卫比没有守卫更坏。** 改成 `[a-z0-9_]+` 才真正会红。
2. **`mutate_guards._apply` 按字节读写**，锚点必须与文件行尾**逐字节**一致。
   `.githooks/pre-push` 在工作区是 CRLF，多行锚点里写 `\n` 匹配不到 → `anchor mismatch`。
   **hook 的变异锚点一律用单行。**

**验证**：`--stage push` **14/14 全绿，28s**；单条自证"恰好一条红 + 还原逐字节一致"。
