## 修复 `.mdx` 指南里的 GFM 表格渲染成纯文本（**未提交**）

线上症状：`/guide/rule-schema` 的 §3.4 字段级参数等 **5 张表**全渲染成
`| 参数 | 说明 | |------|------| | topic | …` 这样一整段原文（用户截图）。

- 根因：`web/components/GuideBody.tsx` 是「一个入口、两个解析器」，按扩展名分发。
  `.md` 分支一直传 `remarkGfm`，`.mdx` 分支调 `<MDXRemote>` 时**一个 remark 插件都没传**。
  而 MDX 的默认管线只有 CommonMark —— 查锁文件坐实：`@mdx-js/mdx@3.0.1` 的 dependencies
  里只有 `remark-parse` / `remark-rehype` / `remark-mdx`，**没有 `remark-gfm`**。
  GFM 管道表格于是不是「表格」，退化成「一段带竖线的普通段落」：**不报错、不抛异常**。
- 修法：把插件收成一份 `sharedRemarkPlugins`（两条路共用 → 不会再各分叉），
  MDX 侧传 `options={{ mdxOptions: { remarkPlugins: sharedRemarkPlugins } }}`；
  并给 `mdxComponents` 补上 `table: Table`（`.md` 侧早有，`.mdx` 侧漏了 → 宽表无横向滚动外框）。

## 仓库重构方案评审（11:00，只评审未动手）

用户提的目标布局：`.cache` / `src/{app,frontend,backend,shared}` / `public` /
`docs`（发布到 /guide）/ `knowledge` / `tools` / `package.json`。

**核对结论：符合 Next.js 16 硬性要求。** 已到源码里坐实，不是凭印象：
`web/node_modules/next/dist/build/index.js` 里 `publicDir = join(dir, 'public')`，
`dir` = package.json 所在目录 → **`src/public` 不会被识别**，public 必须在根。

**必须跟着改的四处**（不改就跑不起来）：

1. `tsconfig.json` 的 `"@/*": ["./*"]` 是相对 `web/` 的，上移后要改成 `"./src/*"`。
2. `web/lib/guide.ts` 的 `GUIDE_DIR = path.join(process.cwd(), "..", "content", "guide")`。
3. `web/scripts/build-knowledge.mjs` 里的 `../knowledge`、`../engine`、`../content/guide` 三个 resolve。
4. EdgeOne Pages 部署根目录从 `web/` 改为仓库根（安装 / 构建 / 输出三处）。

**三个风险点**：

- `functions/` 不能塞进 `src/backend/` —— EdgeOne 边缘函数要求部署根下的**根级** `functions/`
  （现有 `ping.js` / `kv-probe.js` / `issue-probe.js`），挪进去会导致边缘 API 全 404。
- `engine/` 是 Python（rule_engine.py 等），别并进 `src/` 和 TS 混放。
- 现在的 `docs/` 装的是**内部开发文档**（architecture / rules / operations），
  改作"用户文档"前必须先分流，否则会被发到公网 `/guide`。

**给出的分区原则（三个维度分开表达，别再靠目录名猜）**：

- 代码按**运行时**分：`src/app`（路由）/ `src/frontend`（浏览器）/ `src/backend`（站点内服务端 +
  存储接口）/ 根级 `functions/`（边缘）/ 将来的 `server/`（独立后端进程，复用 `engine/`）。
  特别强调 `src/backend` ≠ `server/`，现在不分开，阶段二必混。
- 知识按**域**分：`knowledge/px4`（有构建期派生）+ 收编 `content/skills` → `knowledge/skills`、
  `content/mcp` → `knowledge/mcp`，另开 `knowledge/contributed/` 作外部提交隔离区。
- 文档按**受众**分：`docs/guide`（发布到 /guide，人工 + 自动生成混放）+ `docs/dev`（不发布）。

`docs/guide` 落地推荐**运行时 fs 读**（沿用现有 `lib/guide.ts` 做法），不走构建期生成
page.tsx —— 后者要 gitignore 生成目录、dev 前还得先跑脚本，脚本挂了会留过期页面。
另外：扁平化到根之后 `process.cwd()` 就是仓库根，`docs/`、`knowledge/` 在部署包内，
运行时读文件反而比现在（跨出 `web/` 读 `../content`）**更可靠**。

## 架构建议 v2（11:24，前提变了，结论跟着变）

用户补充两个新前提：**① 网站后续要独立部署 + 提供 MCP 服务；② 知识库要接外部提交，
方式是「引用 git 仓库」或「直接上传 rule/skill」**。并明确"不用借鉴 CLAUDE.md 的固有思维"。

**上一轮"别急着建 server/"的结论作废**——当时前提是"独立部署还远"，现在它是确定的。
已在回复里明说这一点，没藏着。

### 两条硬推论

1. **知识库要接外部提交 → 「读目录」这套必须死。**
   现在 `lib/guide.ts` / `lib/skills.ts` 是运行时 `fs` 读目录，`build-knowledge.mjs` 是构建时
   读目录。外部内容一旦进来：运行时读＝把执行权交给陌生人；构建时读＝收一条社区规则就要
   重新发布整个网站。→ 知识库必须从「源码」升级为**带版本号的制品**，消费方按版本拉取。
2. **MCP 是长连接（SSE）→ 必须有常驻进程。** 而现在 `functions/*.js` 里每行业务逻辑，
   独立部署时都要重写一遍。

### 具体建议

- **registry.lock**：每个条目记 `id / 来源 / sha / 校验和`。**引用 git 必须 pin 到 commit sha
  而不是 branch**——上游一次 force push，你的站点就变了。等价于 lockfile。
- **三条信任等级**：官方（随主仓 CI 全量校验）/ 引用 git（pin sha + 校验和）/ 直接上传
  （沙箱 + 人工审核）。但**三条走同一条校验管线，没有特权通道**。
- **社区提交的是可执行代码，不是文本**：`rules/*.yaml` 的 `expr` / `compute` 被引擎求值，
  Skill 卡片是 MDX 能写 JSX。→ 必须**算子白名单 + 表达式求值沙箱 + MDX 组件白名单**。
  这是安全边界（机器每次都能跑），不是内容审核（人的活）。
- **知识库不建议整体拆成独立仓**：官方规则跟 `engine/operators.py` 的算子强耦合，
  拆仓必然版本错配。→ 官方条目留主仓，社区条目只在 registry 里存指针，内容不进主仓。
- **网站独立部署时不要另写 API 进程**：`next start` 本身就是 Node 服务，route handlers 就是 API。
  → **现在就该把业务逻辑从 `functions/` 往 Next route handler 迁**，这决定将来独立部署的成本。
- **自动生成的 guide 页面别落盘入库**：现在 `build-knowledge.mjs` 往 `content/guide/` 写 .mdx
  并提交 —— 生成物进仓库就是第二份真源。改成构建时生成、路由直接消费。
- 浏览器侧（Pyodide 解析）在两种部署形态下**完全不变**，变的只有服务端。

## 消除 Next.js 的 "inferred workspace root" 警告（12:35）

`next build` / `next dev` 起头报：检测到多个 lockfile，误选了仓库根的
`pnpm-lock.yaml` 当应用根。

**根因**：根 `package.json` 是零依赖纯转发壳，但有人（或平台）在仓库根跑过
`pnpm install`，于是根目录多出一份**空壳** `pnpm-lock.yaml`（importers 只有 `.: {}`）。
它和 `web/` 里真正有依赖的 lockfile 撞车，Turbopack 向上推断时选了更靠上的仓库根。

**修法（标+本一起治）**：
1. 删掉根目录那个空壳 `pnpm-lock.yaml`（git 未跟踪、零依赖所以删了无副作用、不留 diff）。
2. `web/next.config.ts` 加 `turbopack: { root: process.cwd() }` —— 显式把 Turbopack
   应用根钉在 `web/` 自身（本仓库所有 next 命令都经根 package.json 的 `pnpm -C web`
   转发，运行 cwd 就是 `web/`）。给定 root 后 Turbopack 跳过自动推断，即使根目录以后
   又被生成空 lockfile 也不再误判；同时把模块解析 / 缓存 / 文件监听范围收在 `web/` 内。
3. 根 `.gitignore` 加 `/pnpm-lock.yaml`（前导 / 只匹配仓库根，**不**误伤 `web/` 的真实锁）。

**验证**：`next build` 后台跑，日志里确认不再出现该警告文本（同时 31 页照常生成）。

**教训**：根 `package.json` 是 no-deps 壳时，**不要在仓库根跑 `pnpm install`**——
会凭空造出空壳 lockfile，既无用途又触发这个警告。需要装依赖只在 `web/` 里装。
