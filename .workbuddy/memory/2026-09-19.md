## 修复 `.mdx` 指南里的 GFM 表格渲染成纯文本（**未提交**）

线上症状：`/guide/rule-schema` 的 §3.4 字段级参数等 **5 张表**全渲染成
`| 参数 | 说明 | |------|------| | topic | …` 这样一整段原文（用户截图）。

- 根因：`web/components/GuideBody.tsx` 是「一个入口、两个解析器」，按扩展名分发。
  `.md` 分支一直传 `remarkGfm`，`.mdx` 分支调 `<MDXRemote>` 时**一个 remark 插件都没传**。
  而 MDX 的默认管线只有 CommonMark —— 查锁文件坐实：`@mdx-js/mdx@3.0.1` 的 dependencies
  里只有 `remark-parse` / `remark-rehype` / `remark-mdx`，**没有 `remark-gfm`**。
  GFM 管道表格于是不是「表格」，退化成「一段带竖线的普通段落」：**不报错、不抛异常**。
- 修法：把插件收成一份 `sharedRemarkPlugins`（两条路共用 → 不会再各分叉），
  MDX 侧传 `options={{ mdxOptions: { remarkPlugins: sharedRemarkPlugins } }}`；
  并给 `mdxComponents` 补上 `table: Table`（`.md` 侧早有，`.mdx` 侧漏了 → 宽表无横向滚动外框）。

### 顺带证伪了两条写在 `GuideBody.tsx` 里的"硬约束"（都是误诊）

用真实入口 `compileMDX` + `renderToStaticMarkup` 实测（不是读代码猜的）：

1. 原文「表格单元格里不要放 `<Zh>`/`<En>`，MDX 无法解析含 JSX 的 GFM 表格」→ **假**。
   单元格内联 `<Zh>x**粗**y</Zh>`：表格正常成表、`<Zh>` 挂得上组件、`**粗**` 照样加粗。
   当时确实退化了，但**跟 JSX 无关**——真凶就是漏传 `remark-gfm`，不含 JSX 的表格一样退化。
   代价：写内容的人从此绕开表格（`basics.mdx` 用列表代替）。
2. 原文「单行 `<Zh>text</Zh>` 时内部 `**加粗**` 会原样输出星号，必须独占一行」→ **也没复现**，
   单行内联一样渲染出 `<strong>`。`basics.mdx` 里那几处 HTML `<strong>` 是照这条规则写的，非必需。
   （这条**改前是别人的注释，我按实测重写了**；若原作者另有反例，请补充复现步骤。）

## `outputs.check = cpu_load` 的定性（用户追问，01:20）

**结论：不是笔误，是承重的历史名，绝不能"顺手统一"成 group 的 `cpu`。**

证据链（都查过）：

- `group: cpu` 是**执行槽位**（`facts.yaml` 的 `group_order`，决定 finding 的 F01/F02 顺序）；
  `check` 是**报告名**（`checksRun` / `checksSkipped`）。两者本就是两回事，多数规则恰好同名。
- `tools/calibrate/baseline/` 下 **6/6 份**冻结基线的 `checksRun` 都含 `cpu_load`。
  改成 `cpu` 会让 `compare_baseline.py` 在 6 条日志上全红。
- 26 条规则的编译产物里，**25 条 check == group，独此一条不等**；
  构建期 `build-knowledge.mjs:362` 那句 console.log 原文就写着"（显式例外）"——设计如此，非漏门禁。
- 前端只原样透传这个字符串（`web/lib/types.ts`），**没有 check 名 → 文案的映射表**。

**本轮唯一改动**：`knowledge/px4/rules/cpu-load.yaml` 的 `outputs:` 下加 6 行注释，
把上面这段"为什么"写进去。改注释不改值，`build:kb --check` 仍 OK（无漂移）。

**暴露出一个真实的门禁缝隙（未动手，留给后续决定）**：
`compare_baseline.py` 要真实 `.ulg`，在 CI 里是 SKIP 的 —— 也就是说
"把 `cpu_load` 改名"这种破坏基线的改动**云端抓不到**，只有本机 pre-push 兜得住。
可以补一条**纯静态**守卫（不需要 .ulg）：
断言 `baseline/*.json` 的 `checksRun ∪ checksSkipped.check` ⊆ 当前规则编译产物的 check 名集合。

## 新建 /issue 提交页（01:35）

起因：用户报 `https://skill.nextpilot.org/issue` 打不开，并说明这个页面是**用来提交 issue 的**。

**定性：不是坏了，是从来没有过。** 证据：线上 `/issue` → 404（响应体 0 字节）；
`web/app/` 下无该路由；`git log --diff-filter=AD -- web/app/issue*` 无命中；
`next.config.ts` 的 rewrites 里也没有。既有的是 `/api/issues`（POST，405 for GET，正常）
与 `/issue-probe`（200，正常）。

**做了 4 处改动：**

1. `web/components/IssueForm.tsx`（新）—— 分类下拉 + 描述框，提交走**已有的**
   `reportManual()` → `/api/issues`（kind=manual-report），**没有新增任何后端**。
   分类只作文本前缀 `[bug] …` 拼进 note；刻意用 ascii 标签（issue 落到仓库给所有人看，
   不该跟界面语言变）。加结构化字段要动 ALLOWED_KINDS / sanitizePayload / 建单模板 + 一整套自测，不值。
   `reportManual` 要求 ruleIds/findingCount/severityCounts，这里给空值（sanitizePayload 有默认值）。
2. `web/app/issue/page.tsx`（新）—— 照 `login/page.tsx` 的写法：server 组件出 metadata，表单拆成 client 组件。
3. `web/components/SiteHeader.tsx` 的 `SiteFooter` —— 加「提交反馈 / 报告问题」入口，
   否则新页面只能靠输 URL 才能到。
4. `web/e2e/pages.spec.ts` 的 `CRITICAL_PAGES` —— 登记 `/issue`。

**两个必须记住的诚实性问题（都写进代码注释了）：**

- `reportManual` 是 fire-and-forget（不 await、失败静默），所以 UI 只能说"已提交"，不能说"已建单"。
- 线上若没配 `ISSUE_ENABLED`，**整条上报层是 no-op**（见 `web/.env.example`），
  反馈会静默消失 —— 只有 `/issue-probe` 能查出来。
- 脱敏规则在 `lib/error-policy.js`（邮箱/IP/本机路径/token 会被替换），
  所以**明确告诉用户别在这里留联系方式**；issue 公开可见。注释里没复制规则本身
  （谁抄一份，`test-issue-filer.mjs` 会红）。

**验证**：`tsc --noEmit` 全绿；本地 dev（3222）实测 `/issue` 200、
`/definitely-not-a-route` 404 作对照、首页页脚挂上了 `href="/issue"`。
`LanguageProvider` 在 `layout.tsx` 里包着 `{children}`，`useLanguage` 可用。
