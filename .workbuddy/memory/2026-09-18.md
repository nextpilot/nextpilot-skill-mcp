## 调研：`rules/*.yaml` 的字段/语法是怎么校验的（**只诊断，未改**）

- 用户问"是 schema 还是什么"。**结论：全仓库没有 JSON Schema** —— grep `ajv|jsonschema|$schema`
  零命中。是**三层手写机制**
- **第 1 层**：`build-knowledge.mjs:30` 用 `yaml` 包解析，只保证合法 YAML
- **第 2 层（主力）**：`web/scripts/lib/rule-expr.mjs`（954 行）—— compute/when/precheck 是
  **嵌在 YAML 字符串里的 Python 子集 DSL**，所以写了个完整前端：手写 `tokenize()` →
  递归下降 `Parser()`（优先级链 ternary→or→and→not→cmp→arith→term→unary→power→primary，
  刻意对齐 Python：`-2**2 == -4`）→ `infer()` 粗类型推断（scalar/list/**groups**/unknown）
  要点：
  - `fail(msg, src, pos)` 报错带**列号 + 上下文片段**
  - 算子名/元数/选项名查 `ctx.signatures`（真源 `engine/operators.py`）。**校验选项名**是有意为之：
    写错会被 `**kw` 吞掉、算子按默认值静默算出错结果
  - 多输出算子不许嵌表达式中间（值是元组，DSL 里没下标）
  - `topic[:]` → groups（每实例一组），参与四则/比较/三元必报错
  - `checkFirmwareGuards()`：**`FW_MINOR >= N` 必须先判 `is None`**，否则老固件（没写
    ver_sw_release）`None >= N` 抛异常 → 整条规则静默失效。纯领域知识，schema 语言表达不了
  - `UNIT_ALIASES` 是 `engine/rule_engine.py` 的 `_UNIT_FACTORS` 的**镜像**，构建期两边比对，
    不一致直接构建失败（防各改各的）
  - 明确定位"只做校验、不做降级"：不编译、不生成运行期产物
- **第 3 层**：`tools/calibrate/lint_rules.py` 查**字段存在性**。读**构建产物**（`runner._load_rules()`）
  而不是 YAML 原文 —— 老节点写法已在构建期编译掉，产物才是运行期真跑的形态。用 Python `ast`
  抽 `ref(...)` 与 `X.Y`；按规则 `firmware` 圈版本（`fw_matches` 与引擎 `_match_firmware` 同义）；
  证据源 = 回归日志实测字段 + `meta/<tag>.json`。分 OK / version-gap / suspicious
- **为什么不用 schema（可复用的判据）**：① 真正的难点是**字符串里的表达式**，schema 只看得到
  "这是个字符串"；② 约束大量跨文件（算子签名在 operators.py、单位表在 rule_engine.py），
  JSON Schema 表达不了"枚举必须等于另一个文件的字典键"；③ 字段存在性要版本感知 + 读真实日志
- **方向反过来了（这是巧思）**：`/guide/rule-schema` 名字叫 schema，实际是 `content/guide/
  rule-schema.mdx`，**由 build-knowledge.mjs 从 engine/ 源码生成**给人看的文档 —— 不是手写
  schema 约束源码，而是从源码派生文档，所以永不分叉（与 gen_rule_reference 那个 gate 同思路）
- ⚠ **潜在风险（未确认，待用户判断）**：Node 侧 `rule-expr.mjs` 的 parser 与 Python 侧
  `rule_engine._eval_compute` 的 ast 白名单**是同一门语言的两套实现**（构建在 Node、运行在
  Python/Pyodide），没看到保证两者语法认知一致的对拍。若漂移，形态会是"构建过了、浏览器报错"
- 可改进项（建议未采纳）：给 rules yaml 加 `yaml-language-server` 的 `$schema` 提升 IDE 补全，

## 把"校验机制自身的裂缝"落成检查：`tools/ci/check_hygiene.py`

由"今天解决的问题能不能变成检查脚本"引出。现在本仓库的校验是三层：
`check_all.py`（统一入口）→ `check_artifact.py` / `test-issue-filer.mjs`（功能与产物守卫）
→ `mutate_guards.py`（证明守卫会红）+ **`check_hygiene.py`（校验自身的卫生）**。

**新脚本 5 项**（每一项都对应今天踩到的一个"坏掉时没有输出"的裂缝）：

1. **悬空 § 引用** —— 从标题解析"编号文档"（**不维护名单**：名单会过期，标题不会）。
   解析顺序：同行**点名**的文档 → 本文档（若它是编号文档）→ 全局（root `CLAUDE.md` + 任一编号文档）。
   两个关键判据：**只有 `.md`/`.mdx` 可能"自成一册"**（否则 `build-knowledge.mjs` 内嵌的指南页
   模板字符串会替它伪造 25 个章节、`api.py` 注释里的 `# 1.` 也算数）；**"点名"取离引用最近的
   那份文档**（一行提两份是常事，第一个未必是被引的那份）。全仓 **73 处引用全通过**。
2. **产物新鲜度不许用 git 当判据** —— 判据是"该文件**调用**生成器并带 `--check`"（生成器自身
   按路径认定）。第一版用"提到生成器名"当判据，把**测试夹具**（注册表里写着生成器路径）和
   审计它的 `check_hygiene.py` 都误报了。
3. **产物新鲜度门还在** —— 防"目标消失"：门被删掉之后第 2 项会因为找不到目标而恒绿。
4. **打了 FAIL/ERROR 就要能非零退出** —— Python 判"**模块顶层**有没有 `SystemExit`"
   （不是"文件里出现过 `return 1`"：原形里两者并存，而 `main()` 的返回值没人接）；JS 判有没有
   非零 `process.exitCode`。
5. **坏输入必须非零退出**（动态探针）—— `run_checks_locally --probe-data <不存在的日志>` 与
   `mutate_guards --only <不存在的词>`，断言"退出码非零**且**输出含失败标记"。只要非零不够：
   依赖没装、路径写错都非零。

**接线**：`mutate_guards.py` 新增守卫层 `hygiene` + 6 条变异（**共 16 条**）+ 按层跑 `--guard`；

  报它；写 `["git","status",…]` → "git 判据"报它。夹具改成**删掉某一节的编号**（不引入新坏值）。

### **`git status --short` 在这个仓库会漏报 —— 别只信它**

实测：`web/components/LogFlightMap.tsx` 明明与 HEAD 不同（Python 逐字节比对确认），
`git status --short` 却不列它；`git ls-files -v` 也没有 `a`/`s` 标志位（不是 assume-unchanged）。

原因是 **git 的 stat 缓存**：`mutate_guards.py` 改完再逐字节还原，若"改+还原"的间隔太短、
文件大小与 mtime 又落回索引里记的值，git 就**不去重算哈希**，直接当作没变。
（本仓还有 CRLF/LF 归一化警告在刷，也会让 status/diff 的表现变怪。）
**判定"工作区到底干不干净"的可靠顺序**：
`git update-index --refresh` → `git diff --name-only` → 仍不放心就用 Python 直接比
`git show HEAD:<path>` 与磁盘内容。
