### 核过的硬约束（有源码依据，别再凭印象判断）

2. Next.js 的 src 判定 —— `next/dist/lib/find-pages-dir.js`：`findDir` 优先 `./${name}`，
   回退 `./src/${name}`。根有 `app/` 就屏蔽 `src/app`。本方案根不放 `app/`，无此坑。
   （这也是我反对用户最初的"根 `app/` + `src/engine`"方案的依据：将来谁建 `src/app` 会被静默忽略。）
3. `functions/`（EdgeOne 边缘函数）能否进 `src/` —— **未核实**，方案按留根编写。

### 三个隐蔽坑（改错不报错）

1. 根 `.gitignore` 有 `/pnpm-lock.yaml`（注释："仓库根是空壳，不入库"）。
   迁移后真 lockfile 提到根，**这行不删 → CI `--frozen-lockfile` 挂**。
2. `src/lib/content-dir.ts` 是 `path.join(process.cwd(),"content")` —— **运行期**读，
   改错表现为"指南 0 篇 / Skill 0 个"，静默。阶段验收必须手工开页面确认。
3. `tools/ci/mutate_guards.py` 有 29 处 `web` 字面量，扫的是源码文本。改错 → 某条守卫恒真。
   必须跑 `python tools/ci/check_all.py --with-mutate` 让每条先红一次。

### 收益（实测）

- 消掉 4 份双份配置：`.gitignore` / `.prettierignore` / `package.json`（根是 `pnpm -C web` 转发壳）
  / `pnpm-lock.yaml`（根是空壳）。
- `next.config.ts` 的 `turbopack: { root: process.cwd() }` workaround 可删 ——
  它专为"根空 lockfile 与 web/ lockfile 撞车导致 Turbopack 误判 workspace root"而加。

## 目录结构选型：判据与参照（08:2x，用户问"类似项目有什么好结构"）

**判据（本项目）**：顶层目录按「**部署单元 / 运行时**」切，不按语言切，
更不按「web vs 非 web」切 —— 后者是剩余类不是分类，什么都能装，这正是现在乱的根源。

- 会被部署：`src/`、`public/`、`functions/`（Node 配置只在根一份）
- 跨运行时共用：`engine/`（Pyodide + 未来服务端同一份源码）、`knowledge/`（两边都消费的唯一事实源）
- 只在本机：`tools/`、`docs/`

**参照 Langfuse**（pnpm + turbo monorepo：`web/` + `worker/` + `packages/shared/`）：
它按**部署单元**切分，与我们判据一致；但**不照搬**——我们只有一个部署单元，
`deploy.yml` 明确"只上传一个源码目录、由 EdgeOne CLI 自己构建"。
引入 workspace 会让 Pyodide 打包与部署变复杂。**阶段二出现 FastAPI 服务端后再重新评估。**

**PyPA 的 src 提醒**：`src/` 在两个生态里同名不同义 ——
Python 侧 = 放可 import 的包（PyPA 推荐，用于要分发的库）；Next 侧 = 应用源码目录。
所以 `src/engine` 是踩坑；冲刺 4 要把引擎包成 `nextpilot_engine` 时，
Python 侧的正确布局是 `engine/src/nextpilot_engine/`（方向相反）。

**新增风险（已补进方案 §8.4）**：迁移后构建目录从 `web/` 变成仓库根，
部署单元扩到整个仓库 —— `tools/calibrate/logs/*.ulg`（含 GPS）此前是**物理隔离**
（在 `web/` 之外），迁移后只剩 `.gitignore` 一道闸。
**阶段 0 必须先确认 EdgeOne CLI 上传是否严格遵循 `.gitignore`**，否则要补 `.edgeoneignore`。
这是本次迁移新引入的隐私风险，优先级高于其余待确认项。

## 配置归属判据 + Langfuse 实测（08:3x，用户问"Langfuse 是不是根一套 web 一套"）

**判据（写进方案 §2.1）**：配置放在「**覆盖它所需作用域的最小共同祖先**」上。
同名配置出现两份时，**看的是内容是否重叠 + 是否存在工具链强制**，不是看文件数量。
本项目 1 个部署单元 + 1 个 Node 包 ⇒ Node 与 Python 配置各只有一份，都在根。

**Langfuse 实测结论（GitHub API，`langfuse/langfuse@main`）**：根和 `web/` 确实各有一套配置，
但**不重复** —— 根管跨包编排（`pnpm-workspace.yaml`、`turbo.json`、`pnpm-lock.yaml`、
prettier 基线），`web/` 管包自身（package.json 是 workspace 硬要求、tsconfig、eslint、next.config）。
`web/.gitignore` 只有 3 行（storybook 产物），不是根的副本；`web/prettier.config.cjs` 只有 tailwind 插件一行。

**关键差异**：Langfuse 的子包 package.json 是工具链强制；本项目根的 package.json（转发壳）
和 pnpm-lock.yaml（零依赖空壳）**无独立职责**，是"web/ 在子目录"逼出来的影子 → 应删除而非合并。

**别误学**：Prettier 配置向上查找**找到第一个即停、不合并**（官方文档原话
"searching up the file tree until a config file is (or isn't) found"）。
Langfuse 的 web 那份是覆盖根那份，恰好一致属巧合，不是机制保证。

**建议新增守卫（待实施）**：仓库内同名配置文件只允许出现一次，白名单除外；
白名单必须先枚举再定（枚举所有同名配置文件，逐个判定是否工具链强制）。
按 §6.6 自证：在子目录新建一个 tsconfig.json，断言守卫变红。

## monorepo 可行性评估（08:4x，用户问「能不能做成 monorepo」+「web/server/knowledge 三个项目」）

**结论：能做，但现在做 ≈ 0 收益，且提前埋雷。触发条件是 server/ 真需要独立部署。**

### 关键事实（实测）

- **部署上传范围 = `web/` 目录**：`deploy.yml` 两个 job 都是 `working-directory: web`
  + `npx edgeone pages deploy`。→ workspace 兄弟包（`packages/*`）**不在上传范围**，
  web 一旦 `workspace:*` 依赖它们，云端不是 symlink 断，是**压根没有这个包**。
  （我一开始说"symlink 断链"不够准，已修正；此结论与 node-linker 无关，更硬。）
- 项目**无 `.npmrc`** → `node-linker` 默认 `isolated`。
- 根**没有** `pnpm-workspace.yaml`；唯一的 `web/pnpm-workspace.yaml` 内容是
  `allowBuilds` 审批表（解决 `ERR_PNPM_IGNORED_BUILDS`），不是 packages 声明。
- **根 `package.json` 的 description 已写明未来形态**："web/ 是 Next.js 项目，
  server/ 将来是 Python，走 pyproject.toml；不要往这里加 dependencies"。
  → 之前判它"影子/空壳"要修正：它是**有意设计的转发层**，只是没用 workspace 显式化。

### 对用户三分法的判断

- `web/` = Node package ✓（现在就是）
- `server/` = **Python** → pnpm workspace 管不了，要 **uv workspace**（`[tool.uv.workspace]`）。
  且 server 一旦出现就是**第二个部署单元**（EdgeOne Pages 只托管 Next.js 全栈），
  需要独立部署目标。→ 这是多语言 monorepo，比 Langfuse 的纯 TS 复杂一档。
  另注 uv workspace 硬约束：**requires-python 取全体成员交集**，engine 与 server 若要求不同会撞。
- `knowledge/` = **内容资产（YAML/MD），不该变成 package**。理由：它在**构建期**被
  `build-knowledge.mjs` 读（`../knowledge/px4`），不是被 import 的运行时模块；
  且未来 Python 侧也要读它，Python 不认 node_modules symlink → 会变成
  **同一份资产两套解析方式**，比现状更乱。它的"独立"应体现在自有校验脚本（已有）。

### 反直觉结论

**在这里 workspace 不是"提前铺路"，是"提前埋雷"**：现在建了 workspace 只声明 web 一个成员，
未来加 `packages/shared` 被 web 依赖时，立刻撞上"上传范围不含兄弟包"——
要么改上传范围为仓库根（GPS 日志风险），要么绕开 workspace。

### 若真要做，最小动作（不动目录、不改部署）

1. 根加 `pnpm-workspace.yaml`：`packages: ["web"]`
2. 把 `web/pnpm-workspace.yaml` 的 `allowBuilds` **迁到根**并删除 web 那份（避免嵌套 workspace 语义冲突）
3. 根 package.json 脚本 `pnpm -C web xxx` → `pnpm --filter web xxx`
4. CI 里 `pnpm install --frozen-lockfile` 的路径要跟着改

待实测：`pnpm install` 在根与在 web/ 的行为差异（allowBuilds 迁移后是否仍生效）。
