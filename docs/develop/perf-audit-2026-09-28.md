## 二、延迟分解（单次冷启动请求）

```
DNS 查询      0.0007s  ┐
TCP 建连      0.0009s  ├─ 全部可忽略
TLS 握手      0.30s    ┘ ← 唯一的固定成本
TTFB          0.45~0.87s
总计          0.70~0.87s
```

**关键点**：DNS/TCP 在 1 毫秒级，完全不是问题。**TLS 握手 0.30s 是硬成本**，来自「客户端 → 新加坡边缘节点」的跨洋往返（TCP 三次握手 + TLS 两次往返，按 161ms RTT 算就是 3~4 个 RTT ≈ 0.5s 量级）。

ping 实测（直接打边缘 IP `43.174.246.110`）：

```
5 packets transmitted, 4 received, 20% packet loss
rtt min/avg/max/mdev = 161.471/161.683/161.865/0.150 ms
```

> 边缘 IP 段 `43.174.x.x` 属腾讯云**新加坡**。国内用户访问需绕行，这是「备案换国内节点」这个议题的全部物理基础。

## 三、连接复用：TLS 只付一次

这是本次测速最有价值的一组数据——**它修正了此前「每页 0.7s」的口径**。

| 场景              | 耗时         | 说明                       |
| ----------------- | ------------ | -------------------------- |
| 同进程第 1 次请求 | `tls=0.299s` | 完成 TLS 握手              |
| 同进程第 2 次请求 | `tls=0.000s` | **完全复用**，TLS 成本归零 |
| 同进程第 3 次请求 | `tls=0.000s` | 同上                       |

**串行 vs 并行（同一组 5 个页面）**：

| 方式                              | 总耗时      |
| --------------------------------- | ----------- |
| 串行 5 请求（每次独立建连）       | **10.850s** |
| 并行 5 请求（模拟浏览器同时发起） | **2.247s**  |

**差 4.8 倍。** 真实浏览器是 HTTP/2 多路复用 + 并行加载，**用户的体感接近 2.2s 这一档，而不是 10.8s**。此前报告里「单页 0.7s × N」的算法高估了真实体验。

> 已确认协议为 **HTTP/2**（`ALPN: h2,http/1.1`），支持多路复用。

## 五、抖动归因

`/guide` 与 `/` 各连测 20 次：

| 页面     | TTFB min | TTFB p50 | TTFB max | total max |
| -------- | -------: | -------: | -------: | --------: |
| `/guide` |   0.447s |   0.767s |   1.521s |    1.954s |
| `/`      |   0.443s |   0.770s |   1.671s |    2.656s |

**两个页面的 p50 几乎完全一致（0.767 vs 0.770）**，max 的差异（1.52 vs 1.67）也在同一量级。

结论：**抖动来自网络层，不是某个页面的服务端问题**。佐证：

- 全程 `eo-cache-status: Cache Hit`，`age: 711` 持续递增 → 边缘命中，从未回源
- 冷启动测试里出现单次 `tls=1.328s`（正常 0.30s）→ TLS 握手耗时波动 4 倍，这是跨境链路拥塞，与页面无关

`/guide` 此前出现的 3.276s max 是网络长尾，**不需要为它做任何服务端优化**。

## 六、决策建议

### 关于「是否备案换国内节点」

**结论：这已是唯一剩下的杠杆，建议列入计划并评估投入。**

理由：

1. **服务端已无优化空间** —— 静态页耗时与纯静态 CSS/JS 无差异（0.70~0.87s），说明页面生成开销是 0。
2. **前端已无优化空间** —— Brotli 3.3× 压缩、`immutable` 长缓存、plotly 已正确动态加载，首屏实际传输仅 ~240KB。
3. **剩下的只有物理距离** —— 161ms RTT 意味着每次冷启动至少多付 3~4 个 RTT，TLS 握手 0.30s 就是这笔账。换国内节点理论上能把 TTFB 从 0.7~0.87s 压到 **0.1~0.2s 量级，接近 4~5 倍提升**。
4. **这是本次测速得出的关键判断**：既然服务端和前端两条路都走到了尽头，那么「性能还能不能提升」这个问题的答案，**只剩备案换节点这一条**。

**但需先算清代价**：域名实名 + 主体资质 + 约 2~3 周周期；EdgeOne 国内版计费与海外版不同；且一旦备案，站点的合规维护成本会上升。**建议把它作为中期事项推进，而不是应急手段。**

### 已被证伪的建议（留档警示）

初版报告基于「674KB 未压缩体积」提出三条优化建议，**经实测核实全部不成立**：

| 原建议                        | 核实结果                                            |
| ----------------------------- | --------------------------------------------------- |
| ~~给内容页加长缓存~~          | ❌ 静态资源**早已是** `max-age=31536000, immutable` |
| ~~开启 Brotli 压缩~~          | ❌ **已开启**，CSS 压缩比达 6.1×（68KB → 11KB）     |
| ~~HTML 130KB 偏大需内联优化~~ | ❌ HTML 经 br 压缩后约 30KB，属正常范围             |

**教训：体积数字必须区分「磁盘上的文件大小」和「网线上的传输大小」。** 只看 `ls -l` 的 674KB 会得出完全错误的优化方向；必须用 `curl --compressed -w '%{size_download}'` 实测传输量。这一次测量差点让自己去做一件已经做完的事。

## 七、数据可信度说明

- 测量点在**境外沙箱出口**，与国内用户实际体验的链路不同。161ms RTT 是「境外 → 新加坡」的值，国内用户通常更差（需跨境）。
- 单次测量受网络波动影响大（冷启动实测出现过 `tls=1.328s`），报告中 p50 比 max 更可信。
- 并行 2.247s 模拟了浏览器并发，但未包含 DNS 预热、TLS 会话票据（0-RTT）等真实浏览器优化，**真实首屏应优于 2.247s**。
