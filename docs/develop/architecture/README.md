## 一、四层总览

从一份飞控日志到一份中文报告，数据流过四个板块：

```text
① 知识引擎（Python，knowledge/engine/）
   规则框架 + 91 个算子 + 报告数据层
   「怎么算」——与日志格式无关
        │
        │ 构建期拼接（build-knowledge.mjs）
        ▼
② 构建产物（.generated.*）
   引擎内联成浏览器可执行的 Python + 图表/提示词/故障库产物
   「怎么搬」——构建期只搬运，不执行
        │
   ┌────┴────┐
   ▼         ▼
③ Web 应用    ④ MCP 服务
  浏览器 Pyodide   本地 Python（server/）
  「给人看报告」    「给 AI 拿结论」
   web/            server/nextpilot_mcp/
```

**三个关键性质**：

1. **每个板块只认识自己那层**。引擎不认识 topic 名（那是 provider 的事）；
   provider 不懂判定（那是规则的事）；`server/` 不含阈值（那是 `knowledge/` 的事）。
2. **同一份引擎源码，两处运行**——浏览器（Pyodide）与本地工具（`loader.py`），
   不会漂移。
3. **原始日志不出端**。Web 侧全部分析在浏览器完成，没有上传接口。

## 三、根目录与代码的对应

| 目录         | 是什么                                                           |
| ------------ | ---------------------------------------------------------------- |
| `knowledge/` | 知识：引擎机制 + 格式适配 + 规则/图/故障库（**产品的核心资产**） |
| `web/`       | Next.js 站点（独立项目，部署时只上传它自己）                     |
| `server/`    | MCP 服务（stdio）                                                |
| `tools/`     | 开发工具：CI 门禁、引擎回归、日志下载（**产品不依赖它**）        |
| `.githooks/` | 提交与推送钩子（Python 实现）                                    |

> `knowledge/engine/README.md` 是**代码旁的文档**：讲「怎么跑、改完注意什么」；
> 本目录讲「是什么、怎么设计的」。两者分工，不重复。
