# 文档规范与产品资产

代码风格见 [`code-style.md`](code-style.md)；贡献流程见 [`README.md`](README.md)。
本文两件事：文档怎么写、放哪、什么时候删；哪些代码不许当死代码删。

## 1. 文档规范

同一件事在多个文件各讲一遍，改的时候就会漏改其中一处。所以一个主题只有一个详细落点，
其他地方最多一句结论加指向。

落点怎么选：

- 机制类（为什么这么设计、有哪些坑、现在的口径）由该主题的 owner 文档承担，
  同一主题只选一个，选定后别分散。
- 过程类（方案怎么来的、踩过什么）不写进详细落点。方案文档只留需求、结论、待办
  与至今仍起作用的坑。
- 清单类（有哪些检查、各自耗时、挂在哪一阶段）落在清单本身或
  [`../testing/`](../testing/README.md)。

写的时候注意：

1. 不重复贴判据。说明一条守卫拦什么，写一句概括，判据以脚本为准，需要时读源码。
2. 方案文档完结后就地压缩，在顶部写清状态与哪些内容已落到代码里。不迁移、不归档、
   不另建总结。
3. 不乱引用。引用只在读者确实需要跳去读细节时给，且指向真实存在的位置；
   不写「详见上文」「如前述」这类没有落点的引用。
4. 不写历史叙事。事故日期、复现过程、commit hash、谁要求改的，都不进正文；
   结论留下，来历不必留。
5. 不跨文档抄长段。需要另一份文档的内容时给链接，不要拷贝过来。

### 1.1 口吻：像人给同事写的内部文档

AI 生成的文档有一眼可辨的味道：满屏加粗、emoji 状态符号、「四问四文档」式数数标题、
表格塞满一切、开头先讲「本文回答什么问题」、通篇「不要 X 而是 Y」的辩护句。
本仓文档按下面的标准写：

1. 手把手视角。教程按读者操作的顺序写：先说做完会得到什么，然后一步一步做，
   每步给确认点（命令、期望输出）。机制与原理放在步骤之后的专门小节，不打断操作流。
2. 结论先行。对表、盘点类文档第一屏给结论（多少对上了、缺什么、为什么），
   细节清单放后面；读者只看第一段就能带走主干。
3. 正面讲逻辑。解释设计时直接讲它解决了什么问题、带来什么效果；
   不用「为什么不用 X」「不要把 Y 当 Z」的答辩式写法。警告集中放在专门小节，
   不散在叙述里。
4. 收着用加粗。加粗只给关键结论和术语首次定义，一份文档控制在十几对以内；
   叙述里的强调靠句子本身。
5. 不用 emoji 与状态符号。状态用五个词：已有 / 部分 / 占位 / 没有 / 不做。
6. 标题自然。不数数（「三个关键」「四问四文档」），直接说这节讲什么。
7. 表格用在真正的枚举对表上；机制、理由、过程用段落写，一段话能说清的不拆成表。
8. 不元叙述。不写「本文回答一个问题」「先说明」「读法如下」，直接开始讲内容。

### 1.2 文件放哪：八个位置

`docs/develop/` 按读者在什么时刻需要它分八个位置，放错就会造成同一件事两处说法：

| 位置            | 放什么                                                | 生命周期        |
| --------------- | ----------------------------------------------------- | --------------- |
| `README.md`     | 总导航                                                | 长期            |
| `quickstart/`   | 上手与第一个产出：装环境、跑起来、写规则/Skill/MCP    | 长期            |
| `architecture/` | 已落地的机制：边界、契约、schema                      | 长期            |
| `testing/`      | 质量门禁：阶段、分类、守卫、坑                        | 长期            |
| `contribute/`   | 贡献：获取帮助、流程、代码风格、文档规范              | 长期            |
| `knowledge/`    | 领域知识：上游 / 差距 / 覆盖 / 基线                   | 长期            |
| `operations/`   | 运维：部署、环境变量、排障                            | 长期            |
| `roadmap/`      | 计划与决策：`*-plan.md` 进行中，`decisions.md` 已拍板 | plan 完成即处理 |

过程文件（评估报告、重构 plan、复现记录）完成后的处理规则：

1. 把三个月后还要读的结论抽进 `roadmap/decisions.md` 或对应主题的正式文档；
2. 删掉原文件（git 历史里能找回）；
3. 不许把 `*-plan.md` / `*-rework.md` / `*-audit.md` 长期留在任何位置。

判断标准一句话：这份内容，三个月后还需要被人读吗？不需要就删。
决策与未闭合待办一律进 [`../roadmap/decisions.md`](../roadmap/decisions.md)，
不在别处新开文档。

### 1.3 每份 md 的体量

- 一份只讲一个主题；主题讲完就停，不为「完整感」凑节。
- 超过约 300 行就该问要不要拆：能按读者任务拆成两三份的，拆（例：质量门禁拆成
  速查 / 六阶段 / 分类总表 / 守卫 / 日志回归 / 坑六份）。
- 拆出来的目录配一份短 README（导航表 + 全目录里唯一一份的总览），
  子文件之间用相对链接。

## 2. 产品资产：不许以「没人用」为由删

判断一个函数能不能删，看它是不是产品路线的一部分，不看它当前的引用次数。

平台会把高级 Skill 作为付费产品出售，为这条路线预留的能力（电商结构化数据、语音搜索标记、
支付/配额接口等）是先建接口、后接调用，某段时间零引用是正常中间态，不是死代码。

因此：

1. 零引用不构成删除理由。要删先查 `git log -S` 看引入上下文；引入时与一批同主题改动
   一起提交、且注释写明设计意图的，一律按骨架处理。
2. 「暂时用不上」要留接口，不留残迹。留着就要能被下一个人读懂它是什么、将来接在哪，
   而不是留一个让人猜「是不是忘了删」的半成品。
3. 不给「导出必须被引用」之类加门禁。用静态规则固化「零引用 = 该删」的误判，
   会把正在铺的骨架全部打红。
4. 确实要废弃某项能力，需明确说出理由（方向变了 / 被别的方案取代），不能只说「没人用」。

实例：`web/lib/seo.ts` 的 `productJsonLd`（Product + offers，为付费 Skill 的电商富结果预留）
与 `speakableJsonLd`（语音搜索入口，为语音助手分发预留）都是预留资产，按骨架对待，不删。
