# 与上游（Flight Review / ECL EKF Analysis）的能力差

本仓的 PLOT 预设与 PX4 规则是**独立实现的**，不是 Flight Review 的移植。本文记录两边各有什么、
差在哪、哪些差距是设计取舍（不补）、哪些是待补能力。

对比基准（2026-09-30 拉取）：

| 上游                                 | 取用文件                           | 作用                                 |
| ------------------------------------ | ---------------------------------- | ------------------------------------ |
| `PX4/flight_review` @ main           | `app/plot_app/configured_plots.py` | 45 张图表的定义与阈值线              |
| `PX4/flight_review` @ main           | `app/plot_app/plotting.py`         | 图元实现（FFT / 频谱 / 轨迹 / 掉落） |
| `Auterion/ecl_ekf_analysis` @ master | `src/ecl_ekf_analysis/`            | EKF 创新比、内部测试指标的批处理检查 |

> 读法：**"上游有"不等于"我们必须补"**。本仓面向的是"上传日志 → 出结论"的**诊断报告**，
> Flight Review 面向的是"上传日志 → 出 45 张图供人自己看"的**可视化工作台**。形态不同，
> 覆盖面的最优解也不同。每一行差距都在"处置"列给了结论。

## 1. PLOT：本仓 vs Flight Review

### 1.1 数量与构成

|            | Flight Review                  | 本仓 `knowledge/px4/plot/`            |
| ---------- | ------------------------------ | ------------------------------------- |
| 图表份数   | 45 个 `DataPlot` 调用          | 41 份 YAML（含 1 份 `track`）         |
| 其中需 FFT | 3 张 FFT + 3 张频谱密度（PSD） | **0**                                 |
| 其中需地图 | 1 张（`plot_map`）             | 1 张（`track.yml`，`container: map`） |
| 声明方式   | Python 代码硬编码              | YAML 声明 + 构建期校验                |
| 阈值来源   | 代码里写死 `Range1d` / 色带    | `hlines` 声明 + 规则同源              |

### 1.2 本仓有、上游没有

| 能力                     | 本仓做法                                                                           | 说明                                              |
| ------------------------ | ---------------------------------------------------------------------------------- | ------------------------------------------------- |
| **规则与图共用一套取数** | `_ref("新名","旧名")` 候选组、`unit=` 换算、`compute` 算子与 `rules/` 完全同源     | 上游图表直接吃 `topic.field` 字符串，无换名回退   |
| **构建期契约校验**       | `build-knowledge.mjs` 拦：字段引用存在性、`label` 个数对齐、单图单量纲、地图唯一性 | 上游写错要到运行期 `finalize()` 才 `had_error`    |
| **实例区间引用**         | `[a:b]` 闭区间、`[:]` 全实例，`split_by_instance` 决定拆图还是叠线                 | 上游对 IMU 0-3 是逐实例 `change_dataset` 硬写四遍 |
| **老固件字段回退**       | 引用层解决，`sensor_gps` 缺就退 `vehicle_gps_position`，不用写规则                 | 上游在 `helper.py` 里按 `ver_data_format` 分支    |

### 1.3 上游有、本仓没有（按建议处置排序）

**A. 建议补 —— 与"诊断报告"定位直接相关**

| 缺口                        | 上游实现                                                             | 为什么值得补                                                                                                                                               |
| --------------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **振动频谱 / FFT 图**       | `DataPlotFFT` × 3（执行器控制、角速度、角加速度）+ PSD × 3           | 振动是本仓最高频的结论之一，但规则只能给"均值超标"；**装在哪个频点是另一回事**（桨叶通过频率 / 滤波器截止 / 松动起落架）。这是把"超标"升级为"定位"的关键图 |
| **采样规律与丢包图**        | `delta t`（相邻样本时间差）+ `estimator time_slip` + `plot_dropouts` | 本仓只有 `guard-log-dropouts` 一条规则给结论，没有图让人自己看丢在哪个时间段。SD 卡拉胯是极常见的现场问题                                                  |
| **电机转速（RPM）**         | `esc_status` → `Motor RPM`                                           | 本仓 `motor-balance` 用 `actuator_outputs` 推不平衡，有 ESC 遥测的机型可直接看 RPM                                                                         |
| **原始加速度 / 原始角速度** | `sensor_combined` x/y/z 三轴裸线                                     | 上游文档反复强调"多图互证"，裸线是判断振动形态的基础图                                                                                                     |

> 频谱图的实现前提是引擎侧能做 FFT。`knowledge/engine/operators.py` 目前没有频谱算子，
> 需先补一个 `psd()` / `fft()` 算子（跑在 `web/workers/analysis-engine` 还是构建期预计算，
> 要看数据量与首屏预算 —— 见 `docs/develop/decisions.md` D5.4）。

**B. 可选择补 —— 有条件才出现**

| 缺口                                          | 上游触发条件                     | 备注                                                          |
| --------------------------------------------- | -------------------------------- | ------------------------------------------------------------- |
| 空速 vs 地速                                  | `is_vtol` 或有 `airspeed` 数据集 | 本仓只对固定翼/VTOL 有意义，多旋翼上永远是空图                |
| 距离传感器                                    | 有 `distance_sensor` 数据集      | 定高/避障机型才需要                                           |
| 视觉里程计 5 张（位置/速度/姿态/角速率/延迟） | 有 `vehicle_visual_odometry`     | 本仓已有 5 份对应 YAML，**这一项已覆盖**                      |
| 手动控制输入 / RC 原始值                      | 有对应数据集                     | 本仓有 `rc.yml`，**已覆盖**；`manual_control_setpoint` 未覆盖 |

**C. 建议不补 —— 与定位冲突或形态不同**

| 上游能力                             | 不补的理由                                                                      |
| ------------------------------------ | ------------------------------------------------------------------------------- |
| 45 张图全量铺开                      | 本仓是"给结论"，首屏是结论卡不是图墙；全铺会让报告退化成 Flight Review 的劣化版 |
| 参数变更标记（`changed_parameters`） | 上游用于"对照改参前后"，属调参工作台能力，不是事后诊断需求                      |
| 飞行模式背景色 / VTOL 三色底色       | 好交互，但要前端画布支持色带；优先级低于上面 A 组的图                           |
| 3D 视图链接、KML 导出、统计页        | 上游是站点级功能，非单份日志的绘图配置                                          |

## 2. 规则：本仓 vs 上游检查

### 2.1 上游根本没有"规则层"

Flight Review 的 `configured_plots.py` **只画图，不下结论** —— 唯一的判定是振动图的
`add_horizontal_background_boxes(['green','orange','red'], [4.905, 9.81])` 色带，
以及阈值线（`mark_frequency` 标滤波器截止频率）。要得到"这架飞机有问题"的结论，
得人去读图。

`ecl_ekf_analysis` 更接近规则层，但它**只管 EKF**：创新比（`*_test_ratio`）、
EKF 内部测试指标、偏置。它是批处理脚本（`process_logdata_ekf`），输出 JSON，不面向终端用户。

所以本仓的 26 条规则里，**绝大多数没有上游参考对象**，阈值是自定的（注释里标 `[暂定]`）。
这不是坏事 —— 它正是"诊断报告"相对"可视化工作台"的差异化价值。

### 2.2 三边重叠区（可对表）

| 维度         | 本仓规则                                               | Flight Review                  | ECL EKF Analysis         | 阈值是否一致                                          |
| ------------ | ------------------------------------------------------ | ------------------------------ | ------------------------ | ----------------------------------------------------- |
| 高频振动     | `px4-vibration`（均值 ≥ 4.905 警告 / ≥ 9.81 严重）     | 色带同值                       | —                        | **一致**，注释已标来源                                |
| 加速度计削波 | `px4-imu-clipping`（累计 ≥ 100 警告 / ≥ 1000 严重）    | 无独立图，靠裸线看             | —                        | 上游无数值，本仓自定                                  |
| EKF 创新     | `px4-ekf-innovation`（拒绝占比 ≥ 1% 警告 / ≥ 5% 严重） | 无（仅 `estimator_status` 图） | 有检查，阈值在 `params/` | **口径不同**：本仓看"拒绝占比"，上游看单路 test_ratio |
| EKF 硬故障   | `px4-ekf-fault`                                        | 无                             | 有                       | 需对表 ECL 的 fault 位定义                            |
| 估计器标志   | —                                                      | `Estimator Flags` 图           | 有                       | 本仓靠 `ekf-faults` 覆盖                              |
| 失效保护     | `px4-failsafe-*`                                       | `Failsafe Flags` 图            | —                        | 本仓给结论，上游给图                                  |

> **逐条对表见 [`upstream-itemized.md`](./upstream-itemized.md)** —— 上游每一项检查原来怎么写的、
> 本仓现在怎么写的、差在哪，一行一行列出。本文只做**概览**，不要用"超集"这类概括表述替代它。

### 2.3 本仓有、上游完全没有的规则（差异化资产）

**16 个维度、26 条规则**，其中这些是上游两个项目都不做的：

- **电池三件套**：`power-cell-voltage` / `power-remaining` / `power-sag`（上游只有 `Power` 图）
- **电机平衡**：`motor-balance`（上游只有 `Actuator Outputs` 图，结论要人看）
- **姿态跟踪品质**：`attitude-oscillation` / `attitude-overshoot`（上游有 PID 跟踪图，无阈值判定）
- **GPS 三类**：`gps-eph` / `gps-sats` / `gps-jump`（上游有 `GPS Uncertainty` 图）
- **数据质量守卫**：`guard-*` 四条（短日志 / 中途重启 / topic 缺失 / 丢包）—— 上游完全无对应物，
  这是本仓特有的"先判日志能不能用"前置层
- **飞行模式抖动**：`mode-thrash`（上游无）
- **VTOL 转换**：`vtol-transition-attitude`（上游只有转换图，无越限判定）
- **空速健康**：`airspeed-invalid`（上游有图无判）
- **风扰估计**：`wind-estimate`（上游无）
- **日志消息**：`log-errors` / `log-warnings`（上游 `Logged Messages` 是表格，无分级）
- **IMU 零偏漂移**：`imu-bias-drift`（上游无独立图）

### 2.4 建议给上游对表的地方

本仓规则注释里多处标了 `[暂定]`（如 `gps-eph` 的 5.0/10.0 m、`cpu-load` 的 0.90/0.95、
`imu-clipping` 的 100/1000）。这些是**产品可信度的关键**：阈值定错，误报会直接毁掉用户信任。

可对表的上游来源：

| 本仓阈值        | 可参考上游                                                                |
| --------------- | ------------------------------------------------------------------------- |
| 振动 4.905/9.81 | 已对表（Flight Review 色带），**已完成**                                  |
| EKF 创新比      | `ecl_ekf_analysis` 的 `params/` 阈值 ini，以及 PX4 文档的 test_ratio 说明 |
| 电池电芯压降    | PX4 参数 `BAT_CRIT_THR` / `BAT_EMERGEN_THR` / `BAT_LOW_THR`               |
| 姿态振荡/超调   | PX4 PID 调参指南的"跟踪性能"判读标准                                      |
| CPU 负载        | `cpuload.load` 的常见告警线（文档提到 100% 满载风险）                     |

对表结果应回填到各规则的注释，把 `[暂定]` 换成 `[来源]`，与 `vibration.yaml` 的写法统一
（该文件已是范例：注释里写明"阈值 [来源] Flight Review 振动色带"）。

## 4. 结论

1. **PLOT 不缺覆盖率，缺"深度图"。** 41 份预设已覆盖上游绝大多数单量曲线；真正的缺口是
   频谱/FFT、采样规律、ESC RPM 这**四类需要专门渲染器的图**。其中频谱最值钱（把振动结论从
   "超标"推进到"哪个频点"）。
2. **规则是本仓的护城河，不是差距。** 上游不产出结论，本仓 26 条规则里十几条是上游没有的。
   要补的不是"更多规则"，是**给 `[暂定]` 阈值找权威来源**。
3. **最该学的上游实践是"golden log 回归测试"**（`ecl_ekf_analysis` 的做法）：用一批固定日志 +
   固定预期结果，锁住规则行为不漂移。本仓目前 `knowledge/engine/tests/` 只有算子与引擎的单测，
   没有端到端日志回归。
4. **不要往 Flight Review 的形态上长。** 它有 45 张图、3D 视图、统计页 —— 那是工作台。
   本仓的价值是"上传一份日志，给一份能看懂的结论"，图是佐证不是主体。
