# 差距：我们差在哪、哪些不补、该抄什么

对照上游，本仓真正缺的是四件事：频谱、权威阈值、端到端回归，以及一批有意不补的工作台能力。
上游具体有什么见 [`upstream.md`](upstream.md)，本文只对「差距」给结论。

| #   | 差距                          | 量级                           | 处置                      |
| --- | ----------------------------- | ------------------------------ | ------------------------- |
| D1  | 频谱类图表与算子              | 7 张图 + 0 个频谱算子          | 补，唯一硬缺口            |
| D2  | `[暂定]` 阈值缺权威来源       | 15 条规则标 `[暂定]`           | 补，对表上游阈值          |
| D3  | 端到端日志回归                | 引擎有单测，无 golden log 回归 | 补，学 `ecl_ekf_analysis` |
| D4  | 工作台形态能力（3D / 图墙等） | U1 的 45 张图、3D 视图、统计页 | 不补，与定位冲突          |

一个前提要说清：上游有没有，不代表我们必须补。本仓面向「上传日志 → 出结论」的诊断报告；
Flight Review 面向「上传日志 → 出 45 张图供人自己看」的可视化工作台。形态不同，
覆盖面的最优解也不同，所以每一行差距都有明确的处置结论。

## 一、图表：做法的差异与真缺口

上游有哪些图、本仓建了哪些，逐条清单在 [`upstream.md`](upstream.md) 第二节，这里只讲两边做法
的差异和真正的缺口。

两边的构成对比：

|            | Flight Review               | 本仓 `knowledge/px4/plot/`            |
| ---------- | --------------------------- | ------------------------------------- |
| 图表份数   | 45 个 `DataPlot` 构造点     | 40 份 YAML（含 1 份 `track`）         |
| 其中需 FFT | 3 张 FFT + 4 张 PSD         | 0                                     |
| 其中需地图 | 1 张（`plot_map`）          | 1 张（`track.yml`，`container: map`） |
| 声明方式   | Python 代码硬编码           | YAML 声明 + 构建期校验                |
| 阈值来源   | 代码里写死 `Range1d` / 色带 | `hlines` 声明 + 规则同源              |

本仓有、上游没有的四件工程能力：规则与图共用一套取数（`_ref` 候选组、`unit=` 换算、
算子与 `rules/` 同源，上游直接吃 `topic.field` 字符串）；构建期契约校验
（`build-knowledge.mjs` 拦字段引用、label 对齐、单图单量纲，上游写错要到运行期才报）；
实例区间引用（`[a:b]` 闭区间 + `split_by_instance`，上游对 IMU 0-3 是硬写四遍）；
老固件字段回退（引用层解决，上游在 `helper.py` 里按版本分支）。

真缺口按处置分三档：

建议补（与诊断报告定位直接相关）——振动频谱/FFT 图（振动是最高频结论，规则只能给
「均值超标」，频谱才能定位到桨叶通过频率、滤波器截止或松动起落架）；采样规律与丢包图
（现有 `guard-log-dropouts` 规则给结论，没有图让人看丢在哪个时间段，SD 卡问题是现场常见）；
电机转速 RPM（`motor-balance` 用 `actuator_outputs` 推不平衡，有 ESC 遥测的机型可直接看）；
原始加速度/角速度裸线（多图互证的基础）。频谱图的前提是引擎先补 `psd()` / `fft()`
算子——`knowledge/engine/operators.py` 目前没有；跑在 worker 还是构建期预计算，
见 [`../roadmap/decisions.md`](../roadmap/decisions.md) D5。

可选补（有条件才出现）——空速 vs 地速（仅固定翼/VTOL 有意义）、距离传感器
（定高/避障机型）、手动控制输入（`rc.yml` 已覆盖原始 RC，`manual_control_setpoint`
未覆盖；视觉里程计五张已有 YAML 覆盖）。

不补（与定位冲突）——45 张图全量铺开（首屏是结论卡，全铺会让报告退化成 Flight Review
的劣化版）；参数变更标记（调参工作台的能力，不是事后诊断）；飞行模式背景色与三色底带
（要前端画布支持色带，优先级低于上一档）；3D 视图链接、KML 导出、统计页（站点级功能）。

## 二、规则：本仓的差异化所在

Flight Review 只画图不下结论——唯一的「判定」是振动图的三色背景带和阈值线，要得到
「这架飞机有问题」的结论得人去读图。`ecl_ekf_analysis` 更接近规则层，但只管 EKF 一域，
且是批处理脚本输出 JSON，不面向终端用户。

所以本仓 26 条规则里大多数没有上游参考对象，阈值自定（注释标 `[暂定]`）。这正是
「诊断报告」相对「可视化工作台」的差异化价值。

三边可对表的维度：

| 维度         | 本仓规则                                     | Flight Review            | ECL EKF Analysis         | 阈值口径                                    |
| ------------ | -------------------------------------------- | ------------------------ | ------------------------ | ------------------------------------------- |
| 高频振动     | `px4-vibration`（≥4.905 警告 / ≥9.81 严重）  | 色带同值                 | —                        | 一致，注释已标来源                          |
| 加速度计削波 | `px4-imu-clipping`（≥100 警告 / ≥1000 严重） | 无独立图                 | —                        | 上游无数值，本仓自定                        |
| EKF 创新     | `px4-ekf-innovation`（拒绝占比 ≥1% / ≥5%）   | 仅 `estimator_status` 图 | 有检查，阈值在 `params/` | 口径不同：本仓看占比，上游看单路 test_ratio |
| EKF 硬故障   | `px4-ekf-fault`                              | 无                       | 有                       | 需对表 ECL 的 fault 位定义                  |
| 失效保护     | `px4-failsafe-*`                             | `Failsafe Flags` 图      | —                        | 本仓给结论，上游给图                        |

逐条实现差异（上游怎么写的、本仓怎么写的、差在哪）在 [`upstream.md`](upstream.md)
第三、四节，本文不重复。

上游完全没做的规则（本仓 16 个维度 26 条里的差异化资产）：电池三件套
（`power-cell-voltage` / `power-remaining` / `power-sag`）、电机平衡、姿态跟踪品质
（`attitude-oscillation` / `attitude-overshoot`）、GPS 三类（`gps-eph` / `gps-sats` /
`gps-jump`）、数据质量守卫四条（`guard-*`，先判日志能不能用的前置层）、飞行模式抖动、
VTOL 转换越限、空速健康、风扰估计、日志消息分级、IMU 零偏漂移。

关于 D2：`[暂定]` 阈值（`gps-eph` 的 5.0/10.0 m、`cpu-load` 的 0.90/0.95、
`imu-clipping` 的 100/1000 等）是产品可信度的关键，阈值定错，误报直接毁掉用户信任。
可对表的来源：EKF 创新比对 `ecl_ekf_analysis` 的 `params/` 阈值 ini 与 PX4 文档；
电池压降对 PX4 参数 `BAT_CRIT_THR` / `BAT_EMERGEN_THR` / `BAT_LOW_THR`；
姿态判读对 PX4 PID 调参指南；CPU 负载对 `cpuload` 常见告警线。振动 4.905/9.81 已对表完成。
对表结果回填规则注释，把 `[暂定]` 换成 `[来源]`，写法与 `vibration.yaml` 统一
（它已是范例：注释写明「阈值 [来源] Flight Review 振动色带」）。

## 四、结论

1. 图表不缺覆盖率，缺「深度图」。40 份预设已覆盖上游绝大多数单量曲线，缺口集中在
   频谱/FFT、采样规律、ESC RPM 这几类需要专门渲染器的图，其中频谱最值钱——把振动结论
   从「超标」推进到「哪个频点」。
2. 规则是本仓的护城河，不是差距。上游不产出结论，本仓 26 条规则里十几条上游没有。
   要补的不是更多规则，是给 `[暂定]` 阈值找权威来源。
3. 最该学的上游实践是 golden log 回归：用一批固定日志加固定预期结果，锁住规则行为不漂移。
4. 不往 Flight Review 的形态上长。它的 45 张图、3D 视图、统计页是工作台；本仓的价值是
   「上传一份日志，给一份能看懂的结论」，图是佐证不是主体。
