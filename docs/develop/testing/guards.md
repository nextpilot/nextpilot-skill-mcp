| 层             | 文件                                                                                            | 回答                                 |
| -------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------ |
| **单测**       | `knowledge/engine/tests/`                                                                       | 我写的这段逻辑对不对                 |
| **守卫**       | `test-issue-filer.mjs`（23 节）、`check_hygiene.py`（8 项）、`check-site-settings.mjs`（11 条） | 这个不变量还成立吗（扫源码防回潮）   |

第三层是本项目最看重的：**一条永远不红的守卫比没有守卫更坏**，
因为它让人以为有人在看。所以每加一条守卫，就必须同时加一条能证明它会红的变异。

## 自证怎么工作

`tools/ci/mutate_guards.py` 维护一张**变异注册表**：

- 每条变异 = 对某个源文件做一次**精确字符串替换**（锚点是精确字符，不是正则）；
- 注入后跑对应的守卫，断言它**变红**（且只让它红，别的一起红说明判据写宽了）；
- 跑完还原，`git status` 必须干净——超时被硬杀会导致变异残留，务必检查。

`python tools/ci/mutate_guards.py --list` 打印注册表（74 条，按守卫分组）：

| 守卫                                         | 变异数 |
| -------------------------------------------- | ------ |
| 界面侧（`test-issue-filer`）                 | 34     |
| 站点设置（`check-site-settings`）            | 12     |
| 卫生检查（`check_hygiene`）                  | 7      |
| 面板解析器 / 产物侧                          | 6 + 6  |
| SEO 契约 / 拼接命名 / 纯度 / pnpm / APM 版本 | 各 3–4 |
| 指南 MDX                                     | 2      |

34 条打在 `test-issue-filer` 上是它耗时 26min 的原因——所以自证放在独立的
`mutate.yml`，拿自己的超时预算（见 [`checks-by-stage.md`](checks-by-stage.md) §5.3）。

## 历史教训（为什么判据要这么严）

守卫的第一版正则写成 `with_[a-z_]+`，而开关名是 `with_e2e`——
`[a-z_]+` 匹配不到数字 `2`，于是在真实 bug 上跑它报 `OK`。
**一条永远不红的守卫比没有守卫更坏**，因为它还让人以为有人在看。

给守卫写判据时的两条推论：

1. **字符类要覆盖实际字符集**：开关名含数字，字符类就得写 `[a-z0-9_]`；
2. **判据要在真实 bug 上验证会红**，不是在"看起来会红"的样例上验证。
