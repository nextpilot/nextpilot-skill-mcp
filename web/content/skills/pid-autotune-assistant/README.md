# PX4 多旋翼 PID 调参

> 给人看的设计说明。给 AI 看的指令在 [SKILL.md](./SKILL.md)，评分等运营数据在站点上。

## 做什么

给 PX4 **多旋翼**的 PID 增益调整，包括：由内向外的调参顺序、「症状 → 参数」对照表，以及用日志验证的方法。

核心主张：**先排物理问题，再由内向外调增益。** 振动超标、零偏没校准、桨不平衡的时候调 PID，只是在用增益去补偿一个故障——调到"手感稳了"的那一刻，隐患反而更深了。

## 不做什么

| 不管 | 归谁 |
|---|---|
| 怎么判断振动/零偏是否超标 | [`px4-ulog-analyzer`](../px4-ulog-analyzer/)（这里只给出"先确认 gyro_clipping 为 0"这个前提） |
| 参数名叫什么、怎么持久化 | [`px4-parameter-system`](../px4-parameter-system/) |
| 固定翼 PID / TECS | 控制结构完全不同 |
| ArduPilot 调参 | 参数名不同（`ATC_RAT_RLL_*` vs `MC_ROLLRATE_*`），单位约定也不同 |

**限定多旋翼 + 限定 PX4。** 这两刀切下去，覆盖范围变小了，但每一条建议都能具体到参数名和取值方向。做一张"通用调参表"的话，只能给出"适当增大 P"这种没法执行的话。

## 为什么 `capability` 标的是 `config` 而不是 `read-only`

这个 Skill 的输出最终会落到 `param set` 上。把它说成 `read-only` 是误导——用户会以为这只是个"分析工具"。

真实的安全边界是：**输出必须经飞手确认后，才允许写入参数**。SKILL.md 的「使用建议」里这条是不可协商的。同理还有改前 `param dump` 备份。

## 为什么要强调「降增益≠解决问题」

```text
降增益能压住抖动，但会牺牲带宽——那是掩盖问题，不是解决问题。
```

这句话写在 SKILL.md 里，因为它是最容易走偏的地方。抖动时降 D 立刻见效，用户满意离去，但真正的机械/滤波问题还在。三个月后同样的症状会以更严重的形式回来。

对应地，表里有一条是"指导意见"性质的反向条目：

| 症状 | 先试 |
|---|---|
| 高频"嗡嗡响" | 用 `IMU_GYRO_NF_FREQ` 陷波对准机架频率，**不是一味降 D** |

这类"不要做什么"的条目占了表的一半，比例是刻意的。

## 适用版本

以 PX4 v1.14 的多旋翼控制器为准。重要差异：

- **较新固件**引入基于时间常数的写法（`MC_ROLL_TC` 等），逐步替代传统的纯增益 PID。SKILL.md 里明确要求"先确认版本"。
- 旧固件是纯 PID 增益形态。

拿到一台飞控先 `param show MC_ROLL_TC`，存在与否决定了该用哪套参数。

## 验证方法

SKILL.md 反复要求**用设定值 vs 实际值验证，而不是凭手感**。具体比对的字段：

```
vehicle_rates_setpoint.roll   ← 控制器想要达到的角速率
vehicle_attitude.rollspeed    ← 飞机实际达到的角速率
```

这两条曲线的关系是判断的标准：持续滞后 → 加 P；过冲 → 加 D；稳态偏差 → 加 I。

这组字段名依赖 [`px4-ulog-analyzer`](../px4-ulog-analyzer/) 的字段知识，两个 Skill 是上下游关系。
