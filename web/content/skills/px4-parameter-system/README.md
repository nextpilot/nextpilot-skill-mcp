# PX4 参数体系与调参

> 给人看的设计说明。给 AI 看的指令在 [SKILL.md](./SKILL.md)，评分等运营数据在站点上。

## 做什么

回答两个问题：**某个行为该调哪个参数**，以及**改了为什么没生效**。

参数是 PX4 的运行时配置层，几乎所有可调项都在这里。参数名本身没语义，新人常卡在"我知道要改什么行为，但不知道它叫什么"——所以 SKILL.md 给的是「用途 → 参数名」的映射表，而不是参数字典。

## 不做什么

| 不管 | 归谁 |
|---|---|
| 某个参数的**数值**该调到多少 | [`px4-pid-tuning`](../px4-pid-tuning/)（给出的是增益取值逻辑） |
| 增益整定的阶跃响应判读 | [`px4-pid-tuning`](../px4-pid-tuning/) |
| ArduPilot 参数 | 命名完全不同（`ATC_RAT_RLL_P` vs `MC_ROLLRATE_P`），混在一起必然误导 |
| 参数如何用于故障诊断 | [`px4-ulog-diagnostics`](../px4-ulog-diagnostics/) |

**只管 PX4 原生参数。** 这一点写在 SKILL.md 的 `platforms` 里并且再没变过：同样叫"横滚速率环 P"，PX4 是 `MC_ROLLRATE_P`，ArduPilot 是 `ATC_RAT_RLL_P`，单位约定也不同。做一张混表的话，用户按 ArduPilot 的语义去设 PX4 的参数，炸机只是时间问题。

## 为什么把 `param save` 放在最前面

SKILL.md 第一句话就是「`param set` 只在内存生效，必须跟 `param save` 才持久化」。

放在开篇而不是藏在注意事项里，是因为这个错误的**成本极高且不易发现**：调了半小时，手感对了，很满意地断电——第二天回来发现全部白干。而且它不会报错，不会有任何提示。这是 PX4 新人第一大坑，没有之一。

同理，改动前的 `param dump` 备份被写进了流程而不是"建议"。**调参不备份等于放弃了回滚的可能。**

## 适用版本

SKILL.md 里的参数名以 **PX4 v1.14** 为准。跨版本要注意：

- v1.13 及更早：部分参数名不同、单位约定有别（尤其 `BAT_*` 系列改过）
- 涉及时间常数的新形态：`MC_ROLL_TC` 等逐步替代传统的纯增益写法，见 [`px4-pid-tuning`](../px4-pid-tuning/)

## 已知坑

- **参数名长度上限约 16 字符**，超了会被静默截断，`param_find` 失败但不报错。自定义参数命名务必数一下。
- **地面站连接时会同步参数**，可能覆盖你刚在现场改的值。这个坑在"用不同电脑连同一架飞机"的场景里反复出现。
- **换机架必须 `SYS_AUTOSTART` + `SYS_AUTOCONFIG=1` 重启**，否则旧机架的参数残留，行为诡异且难定位。

## 维护

SKILL.md 里的参数速查表如果和 `knowledge/px4/facts.yaml` 冲突，以 **facts.yaml 为准**——那里才是字段字典的唯一真源，这里的表格是给快速查阅用的精简副本。
